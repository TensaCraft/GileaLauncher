# Архітектура

## Крейти

| Шлях | Призначення |
|---|---|
| `crates/launcher-shared` | DTO, події, коди помилок, бренд (`branding`), назви файлів релізу, спільні функції. Збирається і нативно, і під wasm. |
| `crates/launcher-core` | уся логіка лаунчера без Tauri (див. нижче) |
| `crates/launcher-app` | застосунок Tauri: команди, міст подій, аргументи командного рядка, єдиний екземпляр, вікно |
| `crates/ui-kit` | дизайн-система: компоненти, i18n, типізований IPC, звуки, шари, UI-хуки модулів |
| `crates/launcher-ui` | оболонка й сторінки (Leptos CSR), з імітацією бекенда для роботи в браузері |
| `crates/mock-github` | локальна імітація GitHub Releases для перевірки оновлень |
| `modules/*` | опційні модулі (див. [modules.md](modules.md)) |
| `xtask` | збирання, перевірки, хуки, пакування, імітація оновлень |
| `build-profiles/*.toml` | профілі: модулі, бренд, редакція, оновлення |
| `assets/` | переклади, шрифти, фон, звуки, логотип, іконка |
| `tools/` | допоміжні скрипти (синтез звуку кліку) |

`launcher-core` поділено на частини:

| Частина | Що робить |
|---|---|
| `paths`, `storage`, `settings`, `setup` | теки, атомарний запис, конфіг, майстер першого запуску |
| `auth` | Microsoft і офлайн-профілі |
| `minecraft`, `loaders`, `java` | версії, бібліотеки, ассети, Forge/NeoForge/Fabric/Quilt, Java від Mojang |
| `builds`, `content` | збірки та їхній вміст: моди, ресурспаки, шейдери, скриншоти |
| `launch` | запуск гри, реєстр запущених ігор, журнал `running-games.json` (ігри переживають перезапуск лаунчера) |
| `net` | один завантажувач для всього, запити метаданих, перевірка місця на диску |
| `updater` | самооновлення лаунчера |
| `modules`, `providers` | реєстр модулів і контракт провайдера вмісту |
| `feedback`, `logging` | операції, сповіщення, журнал активності, логи з прихованими секретами |

## Як усе пов'язано

```
launcher-ui (wasm) ──ui-kit::ipc──▶ Tauri commands (launcher-app) ──▶ launcher-core services
      ▲                                                                    │
      └──────────── events (launcher-app bridge) ◀── FeedbackService ◀─────┘
```

- **Від інтерфейсу до ядра.** Інтерфейс викликає команди Tauri через типізований IPC з `ui-kit`. `launcher-app` передає виклик далі, сервісам `CoreApp`.
- **Відповіді та стан.** Ядро повідомляє про операції, сповіщення й зміни стану через `FeedbackService`. `launcher-app` перетворює їх на події Tauri, а інтерфейс, отримавши їх, оновлює своє сховище.
- **Команди модулів.** Модулі мають власні команди. Інтерфейс викликає їх через `module_invoke`.

## Бренд і редакції

- **Бренд.** Код не знає назви лаунчера. Під час компіляції `launcher-shared::branding` читає змінні `LAUNCHER_*`, які `xtask` бере з профілю:
  - назву й ідентифікатор;
  - редакцію;
  - репозиторій оновлень;
  - адресу підтримки;
  - налаштування модулів.

  Без профілю діють значення за замовчуванням. `package` так само передає назву й ідентифікатор у Tauri.
- **Редакція** визначає, які модулі має збірка і з яких файлів релізу вона оновлюється (`{name}-{edition}…`). Назви файлів задає одна функція, `launcher_shared::release_file_names`, і нею користуються як апдейтер, так і пакування.

## Теки даних

Теки вибирає `launcher-core::paths`:

- **Налагоджувальна збірка** тримає все в `.dev/` репозиторію. `LAUNCHER_DEV=0` це вимикає.
- **`LAUNCHER_APP_BASE`** — портативний режим: усе в одній теці.
- **Інакше** використовуються системні теки:

| Система | Стан і налаштування | Ігри | Кеш |
|---|---|---|---|
| Windows | `%LOCALAPPDATA%\<name>` | `%APPDATA%\<name>` | `%LOCALAPPDATA%\<name>\cache` |
| Linux | `$XDG_CONFIG_HOME/<name>` | `$XDG_DATA_HOME/<name>` | `$XDG_CACHE_HOME/<name>` |
| macOS | `~/Library/Application Support/<name>` | `…/<name>/minecraft` | `~/Library/Caches/<name>` |

Майстер першого запуску може перенести стан та ігри в іншу теку. Вказівник на неї (`storage.json`) лишається в типовій теці стану.

## Мережа

- **Завантаження.** Усе, що завантажує лаунчер (файли гри, Java, моди, оновлення), іде через `launcher_core::net::downloader`. Він:
  - качає паралельно, з обмеженням;
  - повторює спроби й докачує частково завантажені файли;
  - перевіряє розмір і хеш;
  - перевіряє вільне місце ще до першого байта (`net::preflight`).
- **Метадані.** Невеликі запити (списки версій, маніфести) ідуть через `net::meta`. Відповіді кешуються на годину.
- **Адреси.** Дозволено лише `https`, і це перевіряється на кожному перенаправленні. Звертатися до `127.0.0.1`/`localhost` можуть лише налагоджувальні збірки та збірки з фічею `mock-updates`.

## Самооновлення

1. **Пошук релізу.** `updater::github` читає релізи з `update_repo` профілю. `updater::select` бере найновіший реліз, новіший за запущену версію. Бета-версії враховуються, лише коли ввімкнено «Бета-оновлення».
2. **Вибір файлу.** Береться файл своєї редакції для своєї системи. Якщо такого немає, оновлення не пропонується.
3. **Завантаження.** Файл приходить через спільний завантажувач і звіряється з SHA-256, який віддає GitHub. Потім `updater::stage` готує його до встановлення.
4. **Заміна.** Лаунчер закривається, а його копія в режимі `--apply-update` (`updater::apply`) замінює програму:
   - Windows і Linux: виконуваний файл;
   - AppImage: сам AppImage;
   - macOS: бандл `.app` з образу `.dmg`.

   Якщо заміна не вдалася, повертається попередня версія. Після цього запускається оновлений лаунчер.
